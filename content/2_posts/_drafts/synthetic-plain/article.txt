Most of what follows is the stuff I worked out slowly, by building the wrong thing first. The framework rewards a particular way of thinking and punishes the habits you bring from UIKit.

## State is not a variable

The first thing to internalise is that `@State` is not storage you own. SwiftUI owns it, and your view is a function of it.

```swift
struct CounterView: View {
    @State private var count = 0

    var body: some View {
        VStack(spacing: 16) {
            Text("Count: \(count)")
                .font(.largeTitle.monospacedDigit())
            Button("Increment") {
                count += 1
            }
        }
        .padding()
    }
}
```

The body runs again whenever `count` changes. It is cheap, it is supposed to happen, and trying to avoid it is where most early SwiftUI code goes wrong.

## The view is not the thing on screen

A `View` is a description, not an object. This matters when you reach for a reference to something and find there is nothing to hold.

```swift
// This does not do what a UIKit habit suggests.
let label = Text("Hello")
label.font(.title)   // returns a NEW view; `label` is unchanged
```

Modifiers return new values. Nothing mutates.

## Layout priority is a negotiation

The parent proposes a size, the child chooses one, the parent places it. That is the whole algorithm, and once it clicks, most layout confusion disappears.

```swift
HStack {
    Text("Fixed")
        .layoutPriority(1)
    Text("This one will truncate first when space runs out")
        .lineLimit(1)
}
```

A long single line of code is the case that tests horizontal overflow: `let somethingWithAVeryLongName = someFunction(argumentOne: 1, argumentTwo: 2, argumentThree: 3, argumentFour: 4)`

## What I would tell myself

Build the smallest thing that renders, then add state. Inline code like `@Binding` and `@Observable` will make sense once you have broken something with them.
